## 01. 무엇을 만들었나

업무와 개인 프로젝트처럼 서로 다른 할 일을 공간과 주제로 나누고, 진행 상황을 한눈에 확인할 수 있는 웹 앱을 만들었습니다. 로그인 전에는 브라우저에 목록을 저장하고, 로그인 후에는 같은 계정으로 PC와 휴대폰에서 목록을 공유할 수 있도록 구성했습니다.

단순히 할 일을 추가하고 완료하는 기능에서 시작해, 여러 공간 관리와 계정 동기화까지 기능을 작은 단위로 확장했습니다.

- **정리:** 여러 워크스페이스, 주제별 목록, 이름·이모티콘 수정, 접기와 펼치기
- **실행:** 할 일 추가·수정·완료·기한 설정, 삭제 전 확인
- **확인:** 전체·진행 중·완료 필터, 검색, 완료율과 진행 막대
- **지속 사용:** 새로고침 후 목록 유지, 계정 로그인, 기기 간 동기화
- **문제 대응:** 오프라인 변경 보관과 재전송, 동시 수정 충돌 안내와 병합

## 02. 내가 구현을 이끈 부분

**AI와 함께 코드를 구현하되, 어떤 기능이 필요하고 어떤 동작을 완료 기준으로 삼을지는 직접 정했습니다.** 화면에 기능이 생기는 것에서 끝내지 않고, 실제 사용 흐름에서 결과를 확인하며 개선하는 방식으로 작업했습니다.

### 기능과 사용 흐름

공간 → 주제 → 할 일의 구조로 목록을 정리하고, 선택한 공간에 맞춰 검색과 통계를 표시하도록 구성했습니다. 로그인 없이 시작할 수 있는 브라우저 저장 방식과, 로그인 후 여러 기기에서 이어 쓰는 방식을 함께 마련했습니다.

### 화면과 모바일 사용성

PC와 모바일 화면 크기에 맞춰 주제 카드 배치를 바꾸고, 긴 제목과 이모티콘이 함께 표시되는 상황까지 검토할 수 있도록 했습니다. 완료 상태, 진행률, 저장 상태와 충돌 안내를 화면에서 확인할 수 있게 구성했습니다.

### 서버와 데이터 저장

FastAPI의 HTTP 처리, 요청·응답 모델, 서비스 로직과 DB 연결을 모듈로 나누었습니다. 개발 환경에서는 SQLite를 사용하고, 운영 환경에서는 PostgreSQL을 사용하도록 구성했습니다.

### 인증과 접근 권한

비밀번호를 Argon2로 해시하고, JWT로 로그인 사용자를 확인하는 구조를 적용했습니다. 데이터 요청에 사용자가 임의로 소유자를 지정하지 못하도록 하고, 로그인한 사용자 자신의 목록만 조회·수정할 수 있도록 구성했습니다.

## 03. 내가 검토한 부분

**“기능이 동작한다”는 확인을 넘어, 실패하거나 사용 환경이 바뀌었을 때도 의도한 결과가 유지되는지를 검토 대상으로 삼았습니다.**

| 검토 대상 | 확인 기준 |
| --- | --- |
| 목록 저장 | 새로고침 후 목록과 접힘 상태를 유지하는가 |
| 여러 공간 | 선택한 공간에 해당하는 목록·검색·통계가 표시되는가 |
| 계정 경계 | 다른 사용자의 목록에 접근할 수 없는가 |
| 기존 목록 | 로그인과 로그아웃이 게스트 목록을 덮어쓰지 않는가 |
| 동시 수정 | 다른 기기의 변경을 조용히 덮어쓰지 않는가 |
| 저장 중 추가 편집 | 요청이 진행되는 동안 바뀐 내용도 이어서 저장되는가 |
| 연결 끊김 | 미저장 변경을 보관하고 재연결 후 다시 전송하는가 |
| 모바일 화면 | 긴 제목, 작은 화면, 대화상자에서 가로 넘침이 없는가 |
| 정적 파일 공개 범위 | 비밀 환경 파일과 DB 파일이 웹으로 노출되지 않는가 |

API 테스트와 프런트엔드 상태·동기화 테스트를 함께 마련해, 화면과 서버 사이의 동작을 검토할 수 있는 근거를 남겼습니다.

## 04. 디버깅과 개선 사례

### 사례 A. PC와 휴대폰의 동시 수정 충돌

**문제:** 두 기기가 같은 목록을 수정하면 나중에 저장한 내용이 먼저 저장한 변경을 덮어쓸 수 있습니다.

**구현과 개선:** 서버가 저장 버전인 `revision`을 비교하도록 구성했습니다. 다른 기기에서 먼저 저장했다면 HTTP 409를 반환하고, 화면에서 충돌을 알리도록 했습니다. 사용자는 내 변경을 합치거나 다른 기기의 목록을 선택할 수 있습니다. 서로 다른 항목은 병합하고, 같은 항목의 충돌은 사용자가 병합을 선택했을 때 이 기기의 변경을 우선합니다.

**검토 근거:** 두 클라이언트의 동시 수정, 충돌 중 새로고침, 삭제와 원격 추가가 함께 발생하는 상황을 검사하는 테스트가 있습니다.

### 사례 B. 저장 중 편집과 오프라인 변경 보존

**문제:** 저장 요청을 보낸 뒤 다시 편집하거나 연결이 끊기면, 화면에는 변경이 보여도 서버에 최신 내용이 반영되지 않을 수 있습니다.

**구현과 개선:** 저장 요청 중 추가 편집을 이어서 전송하고, 미저장 변경은 사용자별 로컬 캐시에 보관하도록 구성했습니다. 재접속과 재로그인 후에도 대기 중인 변경을 복원할 수 있게 했습니다. 로컬 백업까지 실패한 경우에는 탭을 닫지 말라는 안내를 표시합니다.

**검토 근거:** 저장 요청 지연 중 추가 편집, 오프라인 복구, 토큰 만료, 로컬 저장 용량 오류를 재현하는 테스트가 있습니다.

### 사례 C. 기기마다 달라지는 이모티콘 정렬

**문제:** 기기의 이모티콘 글꼴과 렌더링 방식에 따라 같은 버튼에서도 그림의 위치와 크기가 다르게 보일 수 있습니다.

**구현과 개선:** 자체 호스팅하는 Twemoji PNG를 사용하고, 그림 영역과 여백을 조정해 버튼 안에서 일관되게 표시하도록 구성했습니다. 요소의 사각형뿐 아니라 실제 그림 픽셀의 중심도 검사 대상으로 삼았습니다.

**검토 근거:** 11가지 화면 크기에서 16개 이모티콘을 검사하며, 실제 그림 중심과 버튼 중심의 차이를 0.6px 미만으로 확인하는 Chrome 검증 스크립트와 별도 WebKit 검증 스크립트가 있습니다. 이 자동화 검사는 실물 휴대폰 검증과는 구분합니다.

## 06. AI 활용과 나의 역할

Codex를 코드 구현, 수정안 작성, 테스트 코드 구성과 오류 분석을 돕는 개발 협업 도구로 활용했습니다. 저는 요구사항과 우선순위를 정하고, 구현 결과를 검토하며, 발견한 문제를 수정 작업으로 이어가는 역할을 맡았습니다.

이 프로젝트에서 강조하고 싶은 역량은 **AI의 제안을 실제 사용 가능한 기능으로 연결하고, 결과를 검토하며 완성도를 높이는 능력**입니다. 코드와 테스트에 남아 있는 구현·검증 사례를 근거로 작업을 설명할 수 있도록 정리했습니다.

AI 활용은 현재 **제작 과정**에 해당합니다. 서비스 내부의 AI 우선순위 추천 기능은 아직 구현되어 있지 않으며, 향후 확장 방향으로 구분합니다.

## 07. 결과와 다음 방향

주제별 투두리스트에서 출발해, 여러 공간과 계정 동기화를 지원하는 웹 앱으로 확장했습니다. 동시 수정, 오프라인, 로그인 만료와 모바일 표시 차이처럼 실제 사용에서 발생할 수 있는 상황을 다루는 구현과 검증 코드를 마련했습니다.

다음 프로젝트에서도 **문제 정의 → AI와 함께 구현 → 결과 검토 → 디버깅 → 검증 근거 기록**의 흐름을 이어가려 합니다.

향후 개선 후보는 AI 우선순위 추천, 접근성 검토 확대, 실물 기기 사용성 확인입니다.
